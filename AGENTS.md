# Руководство по работе с проектом

## Назначение и границы проекта

В корне находится исходный код legacy-компилятора SPHINX C-- 0.239. Он собирает C-- программы в 16/32-битные бинарники, в том числе `.com` для KolibriOS. Каталог `cmm_apps/` содержит реальные программы KolibriOS, которыми проверяется совместимость компилятора.

Главная текущая область риска — новый стандартный приоритет арифметических и битовых операций. Старый C-- часто вычислял цепочки в фактическом порядке слева направо, поэтому часть приложений неявно зависела от старого поведения. То, что программа успешно скомпилировалась, не означает, что ее поведение в KolibriOS осталось правильным.

`cmm_apps/` — отдельный вложенный Git-репозиторий со своим `.git`. Корневой Git видит весь этот каталог как untracked, а изменения внутри него нужно проверять командами `git -C cmm_apps ...`. Не путать его с необычно названным соседним каталогом `cmm_apps/`; рабочее дерево приложений — строго `C:\cmm\cmm_apps`.

Перед любой работой проверить оба состояния и не перезаписывать чужие незакоммиченные изменения:

```powershell
git status --short
git -C cmm_apps status --short
```

## Карта исходников

- `main.cpp` — CLI, загрузка `c--.ini`, общая инициализация и запуск компиляции.
- `tok.h` — центральные типы, глобальное состояние токенов и объявления функций фронтенда/кодогенератора.
- `toka.cpp` — чтение исходника, токены, идентификаторы и препроцессорная часть.
- `tokb.cpp` — загрузка операндов, арифметика, работа с регистрами и значительная часть x86-кодогенерации. Основная runtime-логика приоритета выражений сейчас находится здесь.
- `tokc.cpp` — конструкции языка, объявления, сравнения и управление потоком; здесь есть отдельные пути входа в обработку выражений.
- `toke.cpp` — константные выражения и директивы. Его folding обязан иметь ту же семантику, что и runtime-кодогенерация из `tokb.cpp`.
- `tokr.cpp` — встроенный ассемблер.
- `optreg.cpp` — учет и оптимизация регистров.
- `outpe.cpp`, `outobj.cpp`, `outle.cpp`, `libobj.cpp`, `res.cpp`, `debug.cpp`, `disasm.cpp` — форматы вывода, объекты/ресурсы, листинг и отладочная информация.
- `tests/` — небольшие C-- регрессии для приоритета, скобок и сохранения регистров/стека. Это не автоматический runtime test runner.
- `cmm_apps/lib/` — общая библиотека приложений; ошибка здесь может затронуть много программ.
- `cmm_apps/*/Tupfile.lua` — источник истины для имени входа, выхода и обязательных `/D=...` конкретного приложения.
- `cmm_apps/build.sh` — standalone-массовая сборка всех целей из `Tupfile.lua`.

Код компилятора старый, глобально-состояний и рассчитан на C++03. Не вводить современные возможности C++, не делать попутное форматирование больших файлов и не менять кодировку/окончания строк без необходимости. В старых файлах встречается русский текст в legacy-кодировке; проверять diff после каждого редактирования. Сохранять малый, локальный patch.

Некоторые исходники приложений, в частности `cmm_apps/drvinst/drvinst.c`, записаны в CP866 с CRLF и не являются валидным UTF-8. `apply_patch` не сможет открыть такой файл напрямую. Для минимального изменения допустим только контролируемый round-trip: определить исходную кодировку, временно преобразовать весь файл в UTF-8, внести локальный patch через `apply_patch`, затем вернуть CP866 и CRLF. После этого обязательно проверить, что diff содержит только нужные строки и файл не остался в смешанной кодировке. Обычный `git diff --check` может считать CR в добавленных CRLF-строках trailing whitespace; для таких файлов использовать:

```powershell
git -C cmm_apps -c core.whitespace=cr-at-eol diff --check -- <path>
```

## Сборка компилятора на этом ПК

Полная инструкция для остальных платформ находится в `BUILD.md`. На этом ПК установлен MSYS2 в `C:\msys64`. Для KolibriOS в первую очередь проверять 32-битную Windows-сборку:

```powershell
$env:PATH = "C:\msys64\mingw32\bin;$env:PATH"
i686-w64-mingw32-g++ -w -fno-exceptions -static-libgcc -D_WIN32_ -D__CONSOLE__ -o c--.exe *.cpp
```

PATH обязателен даже при вызове `i686-w64-mingw32-g++.exe` по полному пути: утилитам MSYS2 нужны DLL и вспомогательные программы из того же `bin`.

`C:\cmm` уже добавлен пользователем в Windows PATH. Поэтому нормальный результат сборки — именно корневой `C:\cmm\c--.exe`: после сборки команда `c--` из любого каталога должна запускать свежий компилятор и позволять сразу вручную собирать приложения. Не оставлять новую рабочую версию только под именем `c--.test.exe`. При необходимости убедиться, какой файл найден:

```powershell
Get-Command c-- | Select-Object Source
```

Имя `c--.test.exe` использовать только специально, когда нужно временно сравнить новый компилятор с текущим рабочим `c--.exe` и нельзя его перезаписывать. Оба имени игнорируются Git.

Альтернатива, создающая обычный `c--.exe` и объектные файлы:

```powershell
$env:PATH = "C:\msys64\mingw32\bin;$env:PATH"
mingw32-make -f Makefile.win32
```

64-битную host-сборку делать по `BUILD.md`; она не заменяет обязательную проверку 32-битного компилятора.

## Ожидаемая семантика выражений

Целевой приоритет, от высокого к низкому:

1. унарные операции и скобки;
2. `*`, `/`, `%`;
3. `+`, `-`;
4. `<<`, `>>`;
5. `&`;
6. `^`;
7. `|`;
8. сравнения и логические операции обрабатываются окружающими путями парсера.

Операции одного уровня должны оставаться левоассоциативными. Проверять не только простые переменные, но и константы, отрицательные операнды, вложенные скобки, вызовы функций, аргументы вызовов, сравнения, 8/16/32-битные значения и выражения, начинающиеся с регистра.

При исправлении компилятора помнить о нескольких параллельных путях:

- runtime-выражения и регистры в `do_e_axmath`, `do_e_axmath2`, `doalmath` (`tokb.cpp`);
- константное вычисление/folding (`toke.cpp` и связанные helpers);
- продолжение выражения после `)` и переход к сравнению (`tokb.cpp`, `tokc.cpp`);
- сохранение `EAX`/`EDX`/`ECX`, учет `addESP`, `ClearReg`, `RegToReg` и флаги знания значений регистров.

Каждый `push`/`pop` и временный регистр проверять по всем веткам, включая ранний выход и вложенные скобки. Ошибка учета стека или register tracker часто компилируется без предупреждений, а проявляется только в другом выражении или в KolibriOS.

Выражение в регистр (`EBX = a + b * c`, `EDX = (x << 16) + y`) считает более приоритетный правый операнд или скобки через `EAX` (и `EDX`/`ECX` для `*`, `/`, `%` и счетчика сдвига). Эти регистры сохраняются вокруг вычисления (`SaveScratchRegs` в `tokb.cpp`): в KolibriOS номер функции уже лежит в `EAX`. Какие именно регистры нужны, решает `ScanScratchUse` по тексту операнда. Если выражение начинается с простой скобочной группы и дальше идут только простые операции, группа считается прямо в целевом регистре: адаптированная идиома `(x << 16) + y` дает тот же код, что старая `x << 16 + y`.

Правая часть сравнения может быть выражением в скобках (`a == (b + c)`) или начинаться с числа (`a == 1 + b`; константная часть сворачивается, остаток считается в `EDX`/`ECX`). Байтовое выражение со скобками (`g = (g + 4) & 15`, `g == (a + 4)`) вычисляется в `EAX`, как в C, результат — `AL`. Сам сдвиг на переменную (`EBX = a << x`) и деление в регистр по-прежнему используют `ECX`/`EAX`/`EDX` без сохранения, как и в исходном C--.

## Короткие переходы (`-AJ`)

`-AJ` в командной строке или в `c--.ini` включает автоматический выбор коротких переходов: компилятор несколько раз запускает сам себя (`-AJPASS=<файл>`, реализация в `autojmp.cpp`) и читает каждый `if else while for return break continue goto switch` как `IF ELSE WHILE ...`, кроме тех, что в прошлом проходе не поместились в 127 байт. Такие операторы, в том числе записанные в исходнике заглавными, получают длинную форму вместо ошибки «jump distance too large». Писать `IF`/`WHILE` вручную больше не нужно. Выход нормальной сборки и `-AJ` проверяется сравнением листингов (`-lst`): отличаться должны только кодировки переходов и эквивалентные замены `jcc L; jmp T` → `jncc T` и переход на эпилог вместо его копии. Через `#pragma option` `-AJ` не включается: драйвер работает до разбора исходника.

## Как адаптировать cmm_apps

Не расставлять скобки механически только ради сохранения старого порядка слева направо. Сначала восстановить смысл формулы по окружающему коду, размерам буферов, координатам и индексам. История уже содержит пример, где механическое преобразование `don_w + 10 * don_x + 186` в `((don_w + 10) * don_x) + 186` оказалось неверным; правильным смыслом был `don_w + (10 * don_x) + 186`.

Правило выбора исправления:

- если выражение должно следовать обычному C-приоритету, а компилятор генерирует неверный код — сначала сделать минимальную регрессию в `tests/`, затем исправлять компилятор;
- если приложение действительно зависело от legacy-порядка — явно зафиксировать нужные скобки в `cmm_apps`;
- для длинной адресной арифметики, границ буфера и циклов предпочитать понятные промежуточные переменные (`bound`, `need`, `offset`). Это одновременно документирует смысл и уменьшает нагрузку на хрупкий register codegen;
- после изменения общей библиотеки из `cmm_apps/lib/` найти всех потребителей через `rg` и проверить больше одного приложения.

Особенно внимательно проверять выражения в индексах `ESBYTE`/`ESWORD`/`ESDWORD`, координатах рисования, размерах allocation/reallocation, условиях циклов и KolibriOS syscall-регистрах.

## Диагностика нулевого адреса в KolibriOS

Исполняемый файл KolibriOS начинается сигнатурой `MENUET01`. Если программа неожиданно рисует текст `MENUET01` вместо имени, пути или заголовка, это сильный признак, что строковая функция получила указатель `0` и прочитала заголовок текущего приложения. Сначала искать источник нулевого указателя, а не проблему шрифта или ресурса.

Типичный путь ошибки в приложениях со списками: коллекция пуста или индекс вышел за границы, `collection.get(pos)` возвращает `0`, после чего `WriteText*` печатает `MENUET01`. Перед чтением выбранного элемента и перед обработчиками кнопок проверять `collection.count`/`select_list.count`; пустое состояние должно выводить понятное сообщение и не оставлять активной кнопку действия.

Для `drvinst` список заполняется через `ini_enum_sections` из `/kolibrios/drivers/drvinf.ini`. Если файл отсутствует, недоступен или не содержит разделов, правая панель не должна вызывать `GetCurrentSectionData()` и рисовать данные драйвера. Текущий callback `process_sections(dword sec_name, f_name)` уже соответствует фактической раскладке аргументов C--; не менять порядок параметров только по внешнему виду объявления. При сомнении проверять вызов callback и обращения `[ebp+...]` через `-lst`.

## Проверки

### 1. Минимальная регрессия компилятора

Новый тест должен быть коротким и содержать как проблемную форму, так и явно расставленный эталон. Компилировать свежим корневым `c--.exe` без `-lst`, задавая существующий временный каталог:

```powershell
$checkDir = Join-Path $env:TEMP "cmm-check"
New-Item -ItemType Directory -Force -Path $checkDir | Out-Null
Get-ChildItem tests -Filter *.c | ForEach-Object {
    $out = Join-Path $checkDir ($_.BaseName + ".com")
    & .\c--.exe "/OPATH=$out" $_.FullName
    if ($LASTEXITCODE -ne 0 -or !(Test-Path $out)) { throw "C-- test failed: $($_.Name)" }
}
```

`-lst` генерирует ассемблерный листинг и полезен для разбора кодогенерации, но сам по себе не исполняет тест. Флаг `-v` включает подробный диагностический вывод компилятора. При использовании `/OPATH` не смешивать путь бинарника и путь листинга; проще запускать листинг отдельно в рабочей копии теста.

### 2. Одна программа

Компилировать из каталога программы, повторяя defines из ее `Tupfile.lua`, например:

```powershell
Push-Location cmm_apps\appearance
c-- /D=AUTOBUILD /D=LANG_ENG appearance.c
Pop-Location
```

Такой вызов намеренно проверяет и сам компилятор, и настройку Windows PATH на `C:\cmm`. Если результат неожиданен, сначала проверить `Get-Command c--`.

Наличие непустого `.com` обязательно. Сгенерированные `.com`, `.exe`, `.o`, `.obj`, листинги, логи и `cmm_apps/dist/` не добавлять в commit.

У `drvinst/compile_en.bat` и `drvinst/compile_ru.bat` исторически может быть одинаковый define `LANG_RUS`, поэтому имя batch-файла не считать доказательством выбранного языка. Для явной проверки вызывать компилятор напрямую:

```powershell
Push-Location cmm_apps\drvinst
C:\cmm\c--.exe /D=LANG_RUS drvinst.c
C:\cmm\c--.exe /D=LANG_ENG -lst drvinst.c
Pop-Location
```

Последняя команда оставляет английский `drvinst.com` для ручного тестирования; batch-файлы могут переименовывать результат в `.kex`.

### 3. Все cmm_apps

Запускать через MSYS2 bash. `CMM` должен быть абсолютным POSIX-путем: `build.sh` переходит в каталог каждого приложения, поэтому относительный путь к компилятору перестает работать. Добавление корня в PATH позволяет компилятору найти корневой `c--.ini` и соответствует CI:

```powershell
& "C:\msys64\usr\bin\bash.exe" -lc `
  'cd /c/cmm/cmm_apps && PATH=/c/cmm:$PATH CMM=/c/cmm/c--.exe ./build.sh LANG_ENG'
```

Для изменений парсера/кодогенератора или общей библиотеки прогнать `LANG_ENG`, `LANG_RUS` и `LANG_SPA`, как делает `.gitea/workflows/build.yaml`. Скрипт удаляет и пересоздает `cmm_apps/dist/`, а также пересобирает объявленные `.com`; это ожидаемые generated outputs. Успех — финальные `failed: 0` и непустые цели.

### 4. Runtime в KolibriOS

Массовая сборка — только compile-time gate. Для исправления ошибки запуска необходимо загрузить бинарник, собранный именно проверяемым компилятором и с нужным языком, в KolibriOS и воспроизвести затронутый сценарий. Проверять не только открытие окна, но и действие, где вычисляется измененная формула: рисование/resize, списки и последний элемент, открытие файла, allocation, случайные значения и т. п.

В отчете фиксировать приложение, исходный `.c`, вариант языка, точные шаги, наблюдаемую ошибку/исключение и использованный build компилятора. В этом репозитории сейчас нет настроенного автоматического запуска KolibriOS, поэтому не объявлять runtime-баг исправленным только по успешной компиляции.

## Критерии готовности

- Изменения минимальны и находятся в правильном Git-репозитории.
- Компилятор собирается как 32-битный Windows host binary.
- Существует минимальная регрессия для исправленного случая, и остальные тестовые исходники также компилируются.
- Затронутая программа и полный релевантный набор `cmm_apps` собираются с правильными defines.
- Для runtime-багов выполнена проверка в KolibriOS либо явно указано, что она еще требуется.
- `git diff` не содержит случайной перекодировки, массового изменения строк или generated outputs.
- Финально снова проверены `git status --short` и `git -C cmm_apps status --short`.

## Коммиты и отправка изменений

Корневой компилятор и приложения всегда коммитить и отправлять независимо. Для изменения приложения staging, commit и push выполнять внутри вложенного репозитория, явно указывая только исходники:

```powershell
git -C cmm_apps add -- drvinst/drvinst.c
git -C cmm_apps commit -m "..."
git -C cmm_apps push origin main
```

Для компилятора те же операции выполнять в `C:\cmm` без `-C cmm_apps`. Никогда не добавлять весь `cmm_apps/` в корневой репозиторий и не использовать `git add -A` в каталоге приложений, где обычно лежит много untracked `.com`, `.kex`, `.lst` и build logs. После push проверять, что нужная ветка синхронизирована с собственным `origin/main`; текущие remotes — `cmm.git` для корня и `cmm-apps.git` для вложенного репозитория.
